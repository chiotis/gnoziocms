# Code audit, November 2026 (version 0.1.291)

A review of the code after the shop was finished: security, bloat and speed. The tasks that come out of it are in
[audit-2026-11-tasks.md](audit-2026-11-tasks.md); the ids (S1, P3, B2) are the same in both files.

## What was read, and what was not

Read line by line: the shop's public side (`ShopFront`, `ShopCheckout`, `ShopCustomers`, `ShopCart`, `ShopPricing`, `ShopStock`,
`ShopCoupons`, `ShopOrders`, `ShopPayments`, `ShopDownloads`, `ShopSecrets`, `ShopHttp`), both gateways (`Cardlink`,
`VivaWallet`), the Meta Pixel script, and the parts of `App.php` every request goes through (boot, sessions, CSRF, headers, base
address, the shop's wiring, the work after a response).

Read in part or by search only: `ShopSubscriptions`, `ShopMail`, `ShopMarketing`, `ShopAdmin`, `Images`, `SystemDatabase`,
`PageCache`, `SiteTwig`, the theme's templates.

Not reviewed: the admin screens, MCP, the importers, backups, updates, AI publishing, the admin's JavaScript. Nothing here says
they are fine or not.

Nothing was changed and no test was run. Two things were measured on this checkout (PHP 8.5.3, command line, no opcache): the
application boots in about 73 ms the first time and 20 ms the second time in the same process; opening the database and checking
its 26 migrations takes about 1 ms.

## Overall

The shop's core is careful work. Money is whole cents, prices are worked out again on the server when the order is placed, stock
and coupons are taken with single conditional `UPDATE`s (two shoppers cannot take the last piece), a payment is believed only
after the provider is asked or its digest is checked, the amount and the order number must match, tokens and cart ids are kept
as hashes, secrets are never shown again, and outgoing calls go only to the provider's own hosts. SQL is prepared everywhere I
looked. No class in `src/` is unused.

The problems are around that core: what the site trusts from the request (the `Host` header, `X-Forwarded-For`), what it lets an
anonymous visitor do without limit (sign up, ask for a new password, place orders), what leaves to Meta, and a few places where
a crash or an odd answer from a bank leaves an order or a subscription in the wrong state. On speed, one setting (Twig's cache)
outweighs everything else.

## Security

### High

**S1. Links in emails are built from the request's `Host` header when the site address is blank.**
`App::getBaseUrl()` ([src/App.php:5974](../src/App.php)) uses Settings › site address when it is set; otherwise it takes
`X-Forwarded-Host`, then `Host`, from the request. The default is blank. Whoever sends "forgot password" for a customer's
address with a `Host` of their own gets the reset link mailed to the customer pointing at their site; a click hands them the
token. The same address goes into the verify link, the order's link (with its key), the download links and the gateways' return
addresses. The dashboard already warns about a blank address, but nothing enforces it.

**S2. The order's key and the password token are sent to Meta.**
The Pixel is loaded on every page, including `/checkout/order/{number}?key=…` and `/account/reset?token=…`
([themes/default/layouts/base.twig:172](../themes/default/layouts/base.twig)). Meta's script reports the page's full address
with every event, so Meta receives a key that opens the order (name, address, email, what was bought) and, for an hour, a token
that sets the account's password. It also means a third party's script runs on the pages where a password is typed.

**S3. An answer from Cardlink that is an error is read as "the customer never paid".**
`Cardlink::lookup()` ([src/Shop/Payments/Cardlink.php:237](../src/Shop/Payments/Cardlink.php)) treats any answer without a
status as a failed payment. When an order's time runs out, `ShopCheckout::paidAfterAll()` asks Cardlink; if the bank answers
with an error message (maintenance, a refused digest), the payment is marked failed, the order is cancelled and its stock goes
back on sale, although the customer may have paid. A later answer is noted as "paid after it was cancelled", for someone to sort
out by hand. The XML answer's own digest is also never checked.

**S4. Nothing limits what an anonymous visitor can make the shop do.**
Only signing in is throttled. Without a limit:
- *Signing up* and *forgot password* send an email to any address, as often as asked (and "verify again", once signed in).
- *Placing an order* with bank transfer or cash on delivery sends a confirmation to any address, with a name and a note the
  sender chose: the shop becomes a way to send someone else's text from the shop's own domain.
- *Placing an order* with a card holds its stock for the reserve time. A script can keep every piece of a small shop held, for
  nothing.
- *The Viva webhook* calls Viva's API once for every POST with a well-formed transaction id.

### Medium

**S5. Signing in elsewhere survives a new password.**
A customer's session holds only their id. Setting a new password (by the reset link or in the account), or Google clearing the
password of an unconfirmed account, leaves every other signed-in browser signed in. The case that matters: someone signs up with
a victim's address while confirmation is off, stays signed in, and the victim later signs in with Google into the same account.

**S6. MCP's limits per address can be walked around.**
`App::clientIpAddress()` ([src/App.php:5401](../src/App.php)) takes the first address of `X-Forwarded-For`, which the caller
writes. MCP's per-address limits (the endpoint, registration, the token endpoint) and the address in the activity log use it.
Sign-in throttling uses `REMOTE_ADDR` on purpose; the two should follow one rule, with a setting for the proxies the site trusts.

**S7. No Content-Security-Policy, HSTS or Permissions-Policy.**
`sendSecurityHeaders()` sends `nosniff`, frame options and a referrer policy only. The checkout, the account pages and the admin
have no second line of defence if a script ever gets into a page.

**S8. Payment keys sit as plain text in the database, and so in every backup.**
`ShopSecrets` keeps Viva's API key and client secret, Cardlink's shared secret, Meta's token and WooCommerce's keys in
`system_meta`. A backup sent to S3, or a downloaded one, carries live keys that can refund and charge.

**S9. The admin has no idle time-out and no second factor.**
A session lasts until the browser closes or PHP clears it. The admin can now refund payments, read customers' addresses and
change prices, so a password alone is thin.

**S10. A crash between steps leaves stock held or a subscription stuck.**
- `ShopCheckout::place()` holds stock and counts the coupon before the order is written. If PHP dies in between (time-out,
  memory), the pieces stay reserved with no order to release them.
- `ShopSubscriptions::renewDue()` claims a subscription by making `next_at` negative. If PHP dies during the charge, it stays
  negative and is never picked up again: the subscription silently stops renewing, possibly after the card was charged.
- `changeStatus()` changes the status, then the stock, then the downloads, as separate writes.

### Low

**S11.** Signing up says when an address already has an account (`err_signup_taken`), while "forgot password" takes care not to.

**S12.** The site trusts `X-Forwarded-Proto` and `X-Forwarded-Host` from anyone (`isHttpsRequest()`, `getBaseUrl()`); they
should count only when the request comes from a trusted proxy (the same setting as S6).

**S13.** One token column serves both the verify link and the reset link, so "verify again" cancels a reset that is waiting, and
the other way round.

**S14.** Password hashes brought from WooCommerce (phpass, MD5) stay in the database until that customer signs in. After a few
months they should be cleared, so those customers set a new password by email.

**S15.** A download counts when it starts and cannot be resumed (no `Range`): a broken connection on a large file uses up one of
the customer's downloads.

**S16.** The per-customer limit of a coupon counts orders by email address, so a guest gets round it with another address. It
can only be made firm for coupons limited to signed-in customers.

## Speed

**P1. Twig compiles every template on every request.**
`SiteTwig` creates the environment with `'cache' => false` ([src/SiteTwig.php:90](../src/SiteTwig.php)). Every page that is not
served from the page cache (all of the admin, the cart, the checkout, the account, the first view of every public page) reads,
parses and compiles the layout, the components and each block's template, then runs the result through `eval`, which opcache
cannot keep. This is very likely the largest single cost in PHP for those pages. Not measured here; a before/after on the
checkout and one admin screen will show it.

**P2. A page served from the page cache still boots the whole application first.**
The cached copy is looked for in `App::handle()`, after the constructor has opened the database, checked 26 migrations, loaded
the settings, the theme, the menus' and taxonomies' defaults, the users (`importYamlUsersIfEmpty`, `ensureSuperadminExists`),
Markdown, Twig and the translations. About 20 ms of work (73 ms cold) to send a file. The check can move to `public/index.php`,
before `new App`, for visitors without a session cookie.

**P3. Every public GET ends with a round of "is anything due?" queries.**
`runScheduledAfterResponse()` asks about backups, scheduled entries, pictures, AI schedules, jobs and Omni after each page, and
`formTranslationMigration()->runOnce()` runs before each. One timestamp ("nothing is due before …") would replace them.

**P4. Finding one product loads all of them.**
`ShopCatalogue::byTranslationId()` ([src/Shop/ShopCatalogue.php:540](../src/Shop/ShopCatalogue.php)) builds its table from
every product of the language. Adding to the cart, the cart's JSON, the checkout and every payment return pay for the whole
catalogue. Fine at 50 products, slow at 5,000. The content index already knows where each product's file is.

**P5. Adding to the cart prices the cart three or four times.**
`ShopFront::add()` prices each wanted line, then the whole cart, then (for the Pixel) each wanted line again, then the whole
cart again in `cartSummary()`. Each pass asks the stock table once per line (`ShopStock::forProduct()` keeps nothing). The
account page also reads the customer's orders twice.

**P6. Making picture sizes on demand has no limit on how many run at once.**
`Images::handle()` makes a missing size when it is first asked for. The sizes are a fixed list, which is good, but a crawler or
a script that asks for many at once starts that many encodes (AVIF is heavy). I found no lock in `Images.php`. This is the kind
of load that hurt the Doxiadis server.

**P7. Downloads are streamed by PHP.**
`readfile()` holds a PHP worker for the whole of a 512 MB download. Where the server offers it, `X-Accel-Redirect` (nginx) or
`X-Sendfile` hands the file to the web server and frees the worker (and gives `Range`, see S15).

**P8. Small ones.** `ShopDownloads::sign()` reads its key from the database for every link on a page; every shop request runs
the expired-orders query before anything else (`handleShop()`), which the hourly tick and cron already do.

## Bloat

**B1. `App.php` is 6,142 lines.** It is the router, the admin's controller for most screens, the wiring of every service and a
bag of helpers. It is already on the roadmap (the App split); the shop added about 400 lines of wiring that could move to a
`ShopController` first, as the cleanest cut.

**B2. Three polyfills are loaded on every request and never used.** `vendor/autoload.php` requires the bootstrap files of
`symfony/polyfill-mbstring`, `-ctype` and `-php80`. PHP 8.5 with mbstring (both required) needs none of them. A `replace` entry
in `composer.json` removes them (about 200 KB and three files per request). `public/index.php` also loads Nette's `SmartObject`
by hand, which a correct autoload makes unnecessary.

**B3. The skill's snapshot is a second copy of the theme's blocks, kept by hand.** 168 tracked files under `skills/`, and the
test that compares them is why CI is red now (see below). Making the snapshot when a release is built ends both the copy and the
failures.

**B4. The old name is still in the code.** `X-Faros-Update`, `_faros_check`, `faros-branding`, `FarosMediaPicker`,
`faroscms-*` storage keys and more, in 24 files. Harmless, but each one is a question for the next reader. The header and the
query parameter need an update that accepts both names for one release.

**B5. The starter is 6.1 MB of every release**, most of it two PNGs (1.4 MB, 1 MB), two DOCX files and unoptimised JPEGs.

**B6. Finished plans are still in `docs/`** next to the reference pages (`shop-plan.md`, `mcp-plan.md`, `mcp-shop-plan.md`,
`ai-publishing-plan.md`, `typography-tab-plan.md`, `places-and-routes-v2-plan.md`). The code's comments point at them, so they
should move to `docs/plans/` rather than go.

**B7. Test hooks in production code.** Viva and Cardlink read a `base` address from the secrets to talk to a local fake; it can
only be `localhost`, so it is safe, but it belongs in the test's transport.

**B8. On this machine, not in the repository:** three old worktrees under `.claude/worktrees` (104 MB, detached, they show up in
every search) and `storage/alaleon/` (a site's data in the code's checkout).
